# Снапшот сессии 2026-06-06

Фиксация контекста разработки на конец сессии (по запросу пользователя «сохрани диалог»). Дополняет [[synthesis/project-snapshot-2026-05-14]].

## О чём была сессия

Пользователь поставил задачу: провести **глубокое исследование рынка** для цифрового продукта монастыря (приём церковных записок, пожертвования, история, отзывы/книга жалоб) с целью привлечь больше людей, записок и денег. Затем — составить **ТЗ и пошаговый план** реализации, с акцентом на **пожертвования через целевые программы** (кейс «делаем котельную + фотоотчёт») и **полноценную загрузку HD-изображений с синхронизацией**.

## Что сделано

1. **Многоагентный workflow `monastery-product-research`** (фоновый, ~12 мин): 34 агента, 306 веб-обращений, **112 источников**. 11 направлений разведки (РФ-требы/боты/платежи + западный church-tech/faith-apps + UX/монетизация/история/отзывы/право РФ/правила сторов), адверсариальная верификация ключевых фактов, синтез. Результат → [[synthesis/digital-product-market-research-2026-06-06]].

2. **ТЗ + пошаговый план по дням** → [[synthesis/tz-donations-programs-media-2026-06-06]]. Три модуля: «Пожертвования» (ЮKassa), «Целевые программы» (прогресс + фотоотчёты, пилот «Котельная»), «Медиа-пайплайн» (Yandex Object Storage + imgproxy + CDN). Привязан к реальной структуре `src/` (разведана через Explore-агента).

3. **Старт реализации** (начат в конце сессии) — фронтовый фундамент без бэкенда и без новых npm-зависимостей: media/program/donation типы, хелперы `rub()`/`imgUrl()`, `<ResponsiveImage>`, виджет прогресса, страницы `/programs` и `/programs/:slug` с пилотом «Котельная» на моковых данных.

## Ключевые принятые решения (архитектор)

- **Платформа:** развивать существующий React-сайт → PWA + Telegram-бот; **не** нативное приложение (IAP до 30%, Apple/Google Pay не работают с РФ-картами).
- **Денежное ядро:** подписочное (рекуррентное) поминовение и целевые сборы с прозрачными фотоотчётами.
- **Платежи:** ЮKassa (СБП+карты+чеки 54-ФЗ), рекуррент — CloudPayments. Всё оформляется как «добровольное пожертвование на уставные цели» (нет ККТ по 54-ФЗ, льгота ст.251 НК).
- **Медиа:** оригинал HD → приватный S3-бакет по контентному ключу sha256 (идемпотентность = «синхронизация»); отдача через imgproxy on-the-fly (AVIF/WebP) + CDN; `<ResponsiveImage>` с srcset; массовый импорт — `rclone sync`.
- **152-ФЗ:** подача записок анонимна по умолчанию, email опционально.

## Развенчано верификацией (не использовать!)

- Льгота СБП **0,4% к РПЦ не применяется** — у религиозных организаций МСС 8661 → **0,7%** (0,4% только у благотворительных, МСС 8398).
- Цифра «66% онлайн-пожертвований — рекуррент» — устаревший (2019) самоотчёт CloudPayments, не рыночная норма.

## Текущее состояние кода (на входе в реализацию)

- `src/` — lite-FSD. `features/notes-form` валиден локально, submit отключён (`awaitingBackend=true`) «до Kotlin-бэкенда». Auth-каркас в `features/auth` (Zustand-стор). API-клиент `shared/lib/api/client.ts` с JWT-интерсептором, `BASE_URL = VITE_API_BASE_URL ?? '/api'`. TanStack Query настроен в `app/providers.tsx`. Картинки сейчас — сырые `/photos/*.jpg` без srcset (в `widgets/gallery`, `pages/history/icon`, `meta.ts` MONASTERY_TIMELINE).
- Бэкенд — Kotlin (фреймворк не выбран).

## Следующие шаги (по плану ТЗ)

- Завершить фронтовый фундамент медиа + видимую «Котельную» на моках.
- Согласовать с пользователем зависимости: `@yookassa/checkout-widget`, `blurhash`.
- Неделя 0–1 ТЗ: юр-блок, аккаунты (ЮKassa, Yandex Cloud), бэкенд медиа-эндпоинтов.
- От заказчика нужны: реквизиты организации (`MONASTERY.bank`), договор ЮKassa, аккаунт Yandex Cloud, юр-документы, контент пилота «Котельная», выбор Kotlin-фреймворка.
